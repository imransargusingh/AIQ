## Flow (Rigor Protocol, specialized to component shape)

**Stage 0 — Interdict the rush.** Do not write implementation code. Establish the design and its contracts first.

**Stage 1 — OPEN.** Frame the component: its responsibility (one, ideally), its boundaries, what crosses them, the data it owns vs. borrows, the scenarios and the boundary set (empty/null/max/concurrent/malformed/hostile). **Locate it in the delivery phasing**: which vertical slice of the architecture's phasing plan does this component serve, what is real vs. mocked around it at that phase, and which of its seams must be designed as **mock-substitutable contracts** so the slice deploys end-to-end (test- and human-validatable) before its neighbors are built. In an existing codebase, first establish the **internal contracts** (BoK Part V.1): the local conventions, the existing abstractions, the error style, the test patterns — *find the established pattern and conform to it; a competing one is a recorded deviation.*

**Stage 2 — INTERROGATE.** Drill with precise questions: *Clarification* — what exactly is this component responsible for; *Assumption* — what does it assume about its callers, its data, its concurrency; *Cause/Effect* — what pattern fits this problem and what does choosing it imply; *Evidence* — is the bespoke approach reinventing a standard idiom (Patterns Expert) and does the problem actually need the pattern (Simplifier). Name the candidate patterns (GoF, integration/enterprise, LOA Part IV, language idioms) and the rejected ones. **Climb the Solution-Selection Ladder before naming them** (`solution-selection-ladder.md` L1): does this need to exist (YAGNI) → reuse what already lives in this codebase → stdlib → native platform feature → an already-installed dependency → one line → the minimum that works. The chosen pattern must be the *smallest correct* idiom, and a **new** dependency is justified only past rung 5 (the Gratuitous-Dependency gate). A bounded-but-correct choice (a global lock, an O(n²) scan fine at the current `n`) is recorded as a `simplify:` marker naming its ceiling and upgrade trigger — the code-local sibling of a failure-mode "consciously accept" disposition (L5).

**Stage 3 — EVIDENCE (spikes for the unfamiliar).** **Settle the data model first — it outranks every other decision in this design (`domain-and-data-modelling.md`).** Before the contracts, the endpoints or the tables: state the **conceptual model** this component works in (bounded context, ubiquitous language, entities vs value objects) and the **aggregates** it touches, each with its root and **the one invariant it protects** — boundaries drawn by invariants, not by relationships; small; other aggregates referenced **by identity only**; one aggregate per transaction (DM1–DM3). Then the **durable representation** (DM5–DM6): by default core entities as **dimensions** and change-over-time as **append-only facts**, so history and the audit trail are the data rather than a shadow schema — and for every fact table, measure and projection, **declare the grain before the columns** ("one row is exactly one ______", identified by …, recorded when …), **classify each measure additive / semi-additive / non-additive** (DM9 — summing a balance across time is the standing category error), and **decide the history rule per attribute** (Type-2 whenever a change would rewrite the meaning of a past record; a Type-1 choice is a recorded decision to discard history — DM10). Apply **derive-don't-store** (DM7): facts are stored, aggregates and current-state pointers are computed; any materialised derivation is a labelled, rebuildable cache with a test proving it equals its derivation. Enforce and **test** the append-only and interval invariants (DM11) — including a test that *attempts* a forbidden update, and a rebuild test wherever rebuildability is claimed. Snowflake only with a domain justification (DM12); record the durable-representation choice as an ADR (DM13); and for every persisted field name its **writer and its compute reader** (DM15). Any schema change follows **expand-migrate-contract** with a backfill that never guesses (DM16). The **Data & Persistence Architect holds the hard veto** on an irreversible migration without a backward-compatible path and a tested rollback. **Enumerate the change surfaces this component's data must reach** (`end-to-end-integrity.md` E7): store → domain/model → service → **projection/wire** → client type → UI → compute reader — written down now, so implementation ticks it off rather than discovering the missing projection in production. For every contract the component consumes — and especially anything unfamiliar, preview, or version-sensitive — run the **Spike Protocol** (read + run) and establish it across the BoK Part III dimensions with cited sources. Confirm the error model, nullability, concurrency, idempotency, and resource lifecycle empirically where cheap. For AI-integrated components, name the LOA patterns in play and check the relevant conformance criteria. Map the component's code shape to the **Testing Strategy trigger table** and **enumerate every triggered directive** — D0 hygiene always, then the *union* of every matching D1–D7 / A1–A6. This is a **forcing function, not a mapping exercise**: a triggered directive that the design does not account for is a gate failure (the Test Architect's hard veto) unless a deviation is recorded with rationale. Then design the component's **telemetry to the Observability & Instrumentation Standard** (`observability-and-instrumentation.md`): the spans it opens, the structured log events and the trace context they carry, the stable **error codes** it can emit, the **RFC 9457** problem responses for any HTTP surface, and the metrics (O1–O13). Telemetry is part of the contract — name it now, do not leave it to implementation. **Failure-mode analysis (mandatory).** Derive the failure modes *from the design choices themselves* — every pattern, boundary, dependency, and concurrency decision you just made introduces specific ways to fail. Walk the categories so the common ones are not missed: inputs (null / empty / malformed / boundary / oversized / duplicate / out-of-order); each external dependency (timeout / unavailable / slow / partial or error response / rate-limited / contract drift); concurrency (race / lost update / ordering / partial failure mid-operation); state and data (staleness / inconsistency across stores / partial write / retry idempotency); resources (exhaustion / leak / backpressure); and time (timeout / expiry / clock skew / retry storm). For **each** failure mode, commit to an explicit, intentional disposition — **prevent** (make it impossible by design), **detect** (name the telemetry that surfaces it — an error code, a log, an alert; ties to the Observability Standard), **mitigate / degrade** (fallback, partial service), **recover** (retry, compensate, roll back), or **consciously accept** (with the rationale and the residual risk written down). No failure mode is left implicit: the design states, for each, *how it is addressed or why it is accepted*. Every mode dispositioned as handled and load-bearing becomes a negative/error-path entry in the test plan — these are exactly the cases the urge to complete skips. **Adversarial analysis — STRIDE-lite (mandatory).** Failure-mode analysis covers what goes wrong *by accident*; this covers what goes wrong *on purpose*. Identify the component's **trust boundaries** (every place data or control crosses from a less-trusted to a more-trusted context: public endpoints, queue consumers, file/config ingestion, inter-service calls, admin surfaces), then walk **STRIDE** per boundary — **S**poofing (who could claim a false identity here?), **T**ampering (what data in transit/at rest could be altered?), **R**epudiation (what actions lack attributable evidence? ties to the Observability Standard's audit events), **I**nformation disclosure (what could leak — including through error messages and logs, O-series PII rules), **D**enial of service (what can be exhausted or flooded?), **E**levation of privilege (how could lesser rights become greater?). For **each** identified threat, commit to a disposition exactly as for failure modes — **mitigate** (named control: authn/authz check, validation, signing, rate limit, least privilege), **transfer** (an upstream gateway/platform control, *named*, not assumed), or **consciously accept** (rationale + residual risk written down). Misuse cases for mitigated threats become **negative security tests** in the test plan (the forged token, the tampered payload, the over-privileged caller, the flood). The **Security & Identity Architect holds the hard veto** here, exactly as the Test Architect does for test directives. **Privacy analysis — LINDDUN-lite (mandatory when the component touches personal data).** If any data flow involves a person (directly or by inference), walk **LINDDUN** over it — **L**inkability, **I**dentifiability, **N**on-repudiation, **D**etectability, **D**isclosure (including *through logs and telemetry* — the O-series no-PII rules are a privacy control, verify them here), **U**nawareness, **N**on-compliance (retention, lawful basis, rights paths) — and disposition each finding (mitigate with a named control / accept with rationale + residual risk), recording the data categories touched, retention, and the rights-path mechanism. Findings go in the design's **Privacy analysis (LINDDUN-lite)** section (same table discipline as STRIDE — the repo-level Privacy Review rolls these up mechanically). The **Privacy & Data Governance lens holds the veto** on unanalyzed personal-data flows. If the component touches no personal data, state that in one line — an explicit negative, not an omission. **UI design — interface excellence (mandatory when the component has a user-facing interface, UI Standard U19).** If the component renders a screen, component, flow, page, CLI output, or voice turn, specify the interface, not just the system beneath it: the **medium(s)** and authoritative platform guidelines (U2); the **token references** the UI uses, or the new primitive/semantic/component tokens it defines — no arbitrary values (U3–U5); **capture the token system as the project design-language doc** (`DESIGN.md`, U3a) from `templates/design-language.template.md` — the Stitch DESIGN.md format extended with this pack's floors (contrast audit, complete states, modes, the paired Archetype Signature, motion, perf, AI-UX) — render `templates/design-language-preview.template.html` as the visual catalog, and keep it `scripts/design-lint.py`-clean; seed from an `awesome-design-md` exemplar if useful (`ui-archetype-catalog.md` §J), adapting not cloning (U12); the **key screens/flows** with their visual hierarchy and single focal point (U6); the **complete state set per component** — default / hover / focus / active / disabled / **loading** / **empty** / **error** / **success** plus first-run and overflow (U9, the most common place polish is missing); the **motion** intent with reduced-motion behavior (U10); the **real UI copy** for the load-bearing strings, in the product's voice — no lorem (U11); the **medium adaptation** (how it changes across the declared media); and the **accessibility (WCAG 2.2 AA) and performance-budget** approach (U16–U17). For **AI-facing** UIs, additionally name the applicable **HAX guidelines** (G1–G16 across initially/during/when-wrong/over-time) and the **Shape-of-AI patterns** in play — Wayfinders to defeat the blank canvas, Tuners to shape requests, **Governors** for oversight on consequential actions (action plan before execution, stream-of-thought, controls to steer, verification before irreversible steps), Trust builders (disclosure, caveats, citations, provenance), Identifiers — and design the **wrong answer and uncertainty as first-class states** (effortless correction/regeneration, honest confidence, graceful degradation) (U13–U15). Honor the established pattern for each job unless a deviation is recorded with rationale (U12). The **UX & Accessibility lens co-owns the UI design and holds the accessibility hard veto** (U16). Use the `frontend-design` skill as the hands-on craft companion for web/component media. Maintain the confidence ledger.

**Stage 4 — DISCONFIRM (the gate).** Switch to Adversary Mode. The Patterns Expert and Simplifier check each other (no cargo-cult pattern, no needless abstraction); the Test Architect demands a verification path for every behavior the design promises and attacks coverage gaps with falsifying inputs; Security and Distributed Systems apply their hard vetoes via disconfirming claims; the SRE attacks the **failure-mode analysis** — is every mode dispositioned, is each "accept" actually justified, is each handled mode detectable from telemetry alone and backed by a test? Probe for the *missing* failure mode the analysis didn't list. The **Security & Identity Architect attacks the adversarial analysis** the same way — is every trust boundary identified, is every STRIDE threat dispositioned, is each "transfer" a *named* control rather than an assumption, does every mitigation have its negative security test? An unexamined boundary is a veto. Resolve or record every veto; authors do not self-clear.

**Stage 5 — CONVERGE.** Write the design to `templates/design.template.md`: the **data model** (the aggregates with their roots and invariants; the durable representation; per fact/measure the **grain statement, additivity class and history rule**; the derive-don't-store decisions; the enforced append-only/interval invariants; the migration plan), the contracts (with source citations at the boundaries), the named-and-justified patterns, the data shapes, the error/concurrency model, the **change-surface list** the implementation must tick off (E7), the **failure-mode analysis** (each mode → its disposition: prevent / detect / mitigate / recover / accept, with accepted ones carrying rationale + residual risk), the **adversarial analysis** (trust boundaries; each STRIDE threat → mitigate / transfer / accept, with misuse-case tests for mitigations), the **privacy analysis** (LINDDUN findings → dispositions, or the explicit no-personal-data line) and the **telemetry design** (spans, structured-log events with trace context, stable error codes, RFC 9457 responses for HTTP, and metrics — per the Observability Standard, O1–O13), and the **test plan** (every Testing Strategy directive the triggers select, D0 included — not a sample; every handled failure mode appears as a negative/error-path test). For UI components, also write the **UI design**: token references (or new tokens), the key screens/flows with hierarchy, the **complete per-component state set** (incl. empty/loading/error), motion intent, the real UI copy, medium adaptation, the accessibility + performance approach, and — for AI UIs — the named HAX guidelines and Shape-of-AI patterns (U13–U20). State the residual risk and the flagged unknowns. Name patterns so they will appear in code comments (`// Pattern: … (LOA 3.2)`).
