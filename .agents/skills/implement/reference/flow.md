## Flow (Rigor Protocol, specialized to building)

**Stage 0 — Interdict the rush.** Do not emit a wall of code. Decompose first; build one verifiable slice at a time. **Match ceremony to tier** (`solution-selection-ladder.md` L7): at **T0 (trivial)** run in ladder mode — the least thing that works plus **one runnable check** for any non-trivial logic (an `assert`-based self-check or one small test; a one-liner needs none), code-first with minimal prose, and skip the heavy Proof-Pack / status-table ceremony (running it on a one-line change is its own over-engineering — *Coverage Theater*); at **T1/T2** the full discipline below stands and its durable artifacts are **never** thinned.

**Stage 1 — OPEN (plan tasks).** Decompose the design into small tasks, each independently verifiable, each tracing to a spec statement (Engineering Governance §1). Re-establish the boundary set per task (empty/null/max/concurrent/malformed/hostile). In an existing codebase, confirm local conventions before writing (BoK Part V.1). For changing *existing* untested behavior, **characterize before you change** (BoK §V.2): pin current behavior with characterization tests first. **Climb the Solution-Selection Ladder per task** (`solution-selection-ladder.md` L1) before writing each slice: needs to exist (YAGNI) → reuse the helper/util/type/pattern already here (rung 2 — re-implementing what is a few files over is the most common slop) → stdlib → native platform → an installed dependency → one line → the minimum. Take the first holding rung; a new dependency only past rung 5.

**Stage 2 — INTERROGATE (shape the tests).** For each task, map its code shape to the **Testing Strategy trigger table** (T1–T14) and take the **union** of every matching directive — this is mandatory: a triggered directive is *applied* or a deviation is recorded with rationale, never silently dropped. Apply **D0 hygiene** to every test unconditionally. Ask the Test Architect's questions up front: for each behavior the design promises, what test proves it, and what input makes that test *fail*? A test with no failing input asserts nothing. **Failure-mode analysis (mandatory).** Carry the design's failure-mode analysis forward and extend it with the failure modes your *implementation choices* introduce — the specific libraries, the actual error handling, the concurrency primitives, the parsing/serialization. Walk the same categories (inputs / each dependency / concurrency / state & data / resources / time) so the common error cases are not skipped. For **each** failure mode, the design's disposition must become real in the code — a guard, a typed exception with a stable error code, a fallback, a retry or compensation, a validated boundary — or be consciously accepted with a recorded rationale. Turn every handled mode into a **failing test first** (the null, the timeout, the malformed payload, the concurrent writer, the dependency that errors): these negative and error-path tests are precisely the ones the urge to complete skips, and here they are not optional. **Carry the adversarial analysis forward the same way (STRIDE-lite).** The design's threat dispositions must become real in the code — the authn/authz check, the input validation at the trust boundary, the signed or constant-time comparison, the rate limit, the least-privilege scope — and implementation choices that *create new boundaries or capabilities* (a new endpoint, a deserializer, a file path from input, a subprocess, dynamic SQL) get the STRIDE walk too. Every mitigation gets its **failing negative security test first** (the forged/expired token, the tampered payload, the path-traversal name, the injection string, the over-quota flood). A design-mitigated threat with no enforcing code or no negative test fails the **Security & Identity Architect's hard veto**, exactly as a triggered test directive fails the Test Architect's. **Carry the privacy analysis forward too (LINDDUN-lite):** the design's privacy dispositions become real — the redaction in the structured-log enricher, the retention job, the erasure path, the consent/purpose check — and every mitigation gets its **failing privacy test first** (the no-PII-in-telemetry test with a sample value, the erasure that actually deletes, the export that contains exactly the inventory's categories). Implementation choices that *create new personal-data handling* (a new log field, a cache, an analytics call) get the LINDDUN walk. Unenforced privacy dispositions fail the **Privacy & Data Governance veto**. **Build the UI to the system and prove its states (UI Standard U20, when the component has an interface).** **Honor the spec's UI Archetype Signature** (`ui-archetype-grammar.md` G11): resolve the archetype's codegen descriptor (`ui-archetype-catalog.md`) and apply every facet's rule — the routing/temporal model (`Arch`/`Pacing`: guarded steps, gated progression, no deep-linking past an incomplete gate), the data posture (`Sync`: optimistic-with-rollback / local-first / async-pipeline-with-narrated-wait / server-strict), and the feel (`Feedback`/`Motion`/`Transition`) — so the build is the *same archetype* the spec selected, not a generic regression to the mean. Then build against the **design tokens** — no raw hex, magic numbers, or one-off durations in component code (U3); those tokens are the project **design-language doc** (`DESIGN.md`, U3a) — build to it and keep it `scripts/design-lint.py`-clean (every `{token}` resolves, no arbitrary hex in component code); implement **every specified component state** including the ones the urge to complete skips — **empty, loading, error**, plus disabled/focus/first-run/overflow (U9); honor the platform HIG and the **responsive/adaptive** behavior per medium (U2); wire **motion** with `prefers-reduced-motion` support (U10); use the **real, in-voice UI copy** from the design, not lorem (U11); and meet the **accessibility (WCAG 2.2 AA)** and **performance-budget** floors (U16–U17). Prove these as tests written **red-first**, exactly like security tests: the keyboard-only path, a contrast/labeling check, the empty/error-state render, and a performance-budget threshold assertion (perceived load / interaction latency / frame-rate / payload). For **AI-facing** UIs, make the named HAX guidelines and Shape-of-AI patterns real — the disclosure that content is AI, the correction/regeneration affordance, the action-plan-before-irreversible-action, the citations/provenance — each with its test. A triggered-but-unmet UI directive fails the gate: the **UX & Accessibility lens's veto** for inclusion and state completeness, the Test Architect's for coverage.

**Stage 3 — EVIDENCE (TDD: red → green → refactor).** Work the pair loop, one slice at a time:
- **Red.** Write a failing test that encodes one slice of spec behavior (not the implementation's incidental shape). **Observe it fail** — a test never seen red may be a tautology.
- **Green.** Write the minimum code to pass it. Conform to the Style Guide and the LOA idiom map as you write (`TimeProvider`, `IHttpClientFactory`, Polly v8 `ResiliencePipeline`, `CancellationToken` threaded, no `async void`, no `.Result`; nullable enabled; typed/narrow exceptions). As you write, **instrument to the Observability Standard** (`observability-and-instrumentation.md`): open a span per unit of work; emit **structured** logs (message template + named fields, never interpolated strings) that carry **trace context** (`trace_id`/`span_id` from the active `Activity`); raise every failure with a **stable error code** and, on any HTTP surface, an **RFC 9457** problem response; keep secrets and PII out of all telemetry (O1–O13). Name patterns in comments (`// Pattern: … (LOA 3.2)`). Mark every deliberate bounded shortcut with an inline **`simplify:`** comment naming its ceiling and upgrade trigger (`solution-selection-ladder.md` L5) — the code-local form of a recorded deviation, harvestable into the debt ledger.
- **Refactor.** Improve structure with the tests as a safety net; keep the suite green in small steps; never mix a refactor and a behavior change in one silent commit (BoK §V.2).
- If a contract turns out to be unfamiliar, **spike it** (`spike-protocol.md`) before coding against it, then make the spiked behavior a real test.

Reach for the wider toolkit when cost-of-error warrants (Testing Strategy): property-based tests for wide input domains, contract/schema tests at boundaries (D5/D6), characterization tests for legacy, mutation testing to answer *"does the suite fail when the code is wrong?"*. For AI-integrated code: split deterministic structure checks from probabilistic content evals (A1–A6); treat prompt/schema/tool-description changes as contract changes with a regression gate (A6).

**Stage 4 — DISCONFIRM (pre-merge review).** Switch to Adversary Mode. The Test Architect attacks coverage: mutation sense (would a flipped `+`/deleted guard/`&&`→`||` be caught?), boundary coverage, tautologies, mock fiction, flaky/non-deterministic tests, probabilistic exact-match. **This is a hard gate: any triggered Testing Strategy directive that was not applied — and not deviation-recorded — fails the review.** The Test Architect and SRE also confirm that **every failure mode from the analysis is handled in code and proven by a negative/error-path test** (or its acceptance is recorded with rationale), and probe for the failure mode that was missed. Run mutation tooling where configured and address survivors. The language Developer attacks idiom and async correctness. The SRE attacks the instrumentation against the Observability Standard: are logs structured and trace-correlated, does every failure carry a stable error code, do HTTP errors return RFC 9457, is any secret or PII leaking into telemetry (O1–O13)? Resolve the Test Architect's **hard veto**; the author does not clear it. The **Simplifier** runs its delete-list pass over the diff — one line per finding tagged `delete:` / `stdlib:` / `native:` / `yagni:` / `shrink:`, ending `net: -<N> lines possible` — and an applicable lower ladder rung skipped without a recorded reason is a Simplifier finding (L9); a single smoke/`assert` self-check is the minimum, never flagged.

**Stage 5 — CONVERGE (verify & report).** Demonstrate correctness against the spec's success criteria and the boundary set — not merely a green suite. **Tick off the change-surface list** the design enumerated (`end-to-end-integrity.md` E7): store → domain/model → service → **projection/wire** → client type → UI → **compute reader**, and for every new or changed field confirm it has a traced **writer** and a traced **compute reader** (E8) — round-trip tests prove neither. Prove the **rendered surface**, not only the units: at least one test goes through the **real composition root** to the real surface a user touches (E11), and where a quantity appears on more than one surface, a **cross-surface consistency** test asserts the surfaces agree with each other (E12). Verify any new surface is **reachable** from where the user actually is (E10). Produce the **Proof Pack** (Rules of the Road §3.1): one row per correctness claim — claim, evidence (test name/assertion/run output), source/`file:line`, oracle (why it can fail), red-observed (seen to fail before the fix), confidence, residual risk. Re-ground against the spec (BoK §VI.2): confirm no drift, no contradicted earlier decision. **Register what went wrong** (`continuous-improvement.md` CI1): any defect introduced during this build, any assumption that proved false, and any correction received becomes a **class** entry in `docs/lessons/defect-classes.md` with its control. Record any deviations (Rules of the Road §4).

**Close with the status table (mandatory).** End the response with:

| **Remaining** | the tasks or phases still unimplemented (per the design and the architecture's phasing plan) |
