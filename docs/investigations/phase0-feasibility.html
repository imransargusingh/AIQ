Spike: Phase 0 feasibility (task grouping, job, rung)

Verdict: GO to real-data validation, with two design changes. On synthetic data, all three questions pass for rungs 1 to 3. Rung 5, and half of rung 4, need signals that are not in session transcripts. Job classification needs a short prompt excerpt; structured signals alone are not enough.

What was tested

  • Reader. prototypes/phase0-spike/aiq_spike/normalize.py reads both surfaces into one list of human

turns. It reuses AI-Forward's session-profile.py for discovery and parsing (claude_sessions, copilot_sessions, _load_events, _text_of, _tool_result_texts, _args_of) by loading it from the installed pack, not by copying it. All 107 labelled turns were recovered from both formats.

  • Corpus. Two synthetic corpora in the on-disk formats AIQ will read

(~/.claude/projects/<slug>/<session>.jsonl, ~/.copilot/session-store.db + session-state/<id>/events.jsonl). No real person's data was read.

  • Dev: 30 hand-written tasks in 14 sessions, 66 turns (14 Code a change, 10 Write a spec or doc,

6 other jobs; rungs 1 to 5). The session plan is designed to be hard: several tasks per session a few minutes apart, a task resumed hours later on the other surface, a 70-minute idle gap inside one task, and a design note followed by its implementation on the same feature.

  • Held-out: 20 tasks in 10 sessions, 41 turns, written by a separate Sonnet call that never saw

the dev tasks, the grouper or the judge (prototypes/phase0-spike/data/heldout_scenarios.json). Different domain (rail timetabling), terser phrasing.

  • Grouping. Three strategies: a 5-minute gap baseline, a deterministic heuristic (time gap,

shared files, prompt similarity, cue words), and one model call that assigns every turn in the window to a task.

  • Judge. One call per task returns job, current rung, potential rung, confidences, evidence, gap

and blockers against the design doc's rubric (prototypes/phase0-spike/aiq_spike/judge.py). Two input modes:

  • signals: counts and flags only (prompts, re-prompts, structure markers, tools, tests and

checks run, sub-agents, file kinds). No prompt text and no paths.

  • excerpt: signals plus each prompt cut to 300 characters (at most 8), file paths, and commands

the agent ran.

  • Models. Claude Haiku 5.5 and Sonnet 5.5 through the local claude -p with tools, settings and

MCP off, and schema-checked JSON output. This matches ADR-0007 on the architecture branch (judge runs through the person's own AI account). Every configuration ran twice to measure repeatability. Judging used the gold task grouping, so judge errors are measured apart from grouping errors.

The product rule is Unclassified when the job is "other" or confidence is below the pack threshold. With excerpts and a threshold of 0.7:

  • Precision on classified tasks was 100% in all four excerpt runs.
  • No other-job task reached an alpha pack.
  • 80 to 97% of alpha-job tasks were classified. The rest fell back to core Opportunities, which is

the designed safe failure (US-7).

The misclassified tasks were short and context-free: a one-line typo fix, and a pasted snippet with "what's wrong with this". The judge gave them low confidence (0.4 to 0.6), so a 0.7 threshold routes them to Unclassified rather than the wrong pack.

Recommendation: set the alpha pack threshold at 0.7. The judge needs the minimised excerpt to classify the job. ADR-0007 already sends task content to the person's own model account, so this costs no extra privacy. It should still be shown in the capture log and be possible to turn off. With the excerpt off, expect about 20% wrong jobs.

  • Rung 5 cannot be seen in a transcript. The judge always saw the typed slash command and the

checked-in workflow file. It noted both, then stopped at 3 or 4, because the rubric requires that "others can trigger it", and nothing in the session shows that. This is the rubric working as written, not a model failure. AIQ needs a reuse signal from the repo: is the workflow file versioned, how many authors has it had, and do CI or other people's sessions run it (counts only, as the design doc's Reuse signals already say).

  • Rung 4 is judged one rung low half the time. Two Sonnet runs on two of the four rung-4 tasks

called them 3, despite sub-agents, a spec and automated gates. Fix the rubric wording before tuning the model: say what counts as "several agents coordinated" when the sub-agents are visible.

  • Signals-only mode biases low by about half a rung. It also reaches only 53 to 60% exact.

Prompt structure is the main signal for rungs 1 to 3, and counts cannot carry it.

  • Potential rung was within one rung in 100% of Sonnet excerpt runs. For coaching, the judge

flagged 95 to 100% of tasks that have a next rung (recall). But 15 to 27% of its "next rung" calls were tasks already at their right rung (precision 0.73 to 0.85). The coaching loop should not nudge on potential until precision is measured on real data. Coaching only on potential-confidence ≥ 0.8 is the first thing to try.

  • Haiku is cheaper but less stable. It costs about $0.001 per task against about $0.01 for

Sonnet (list-rate estimates reported by the CLI; on a subscription this is quota, not dollars). Its rung agreement between two runs was 0.83 to 0.90, against 1.00 for Sonnet, and held-out exact accuracy dropped to 0.55. Sonnet answered in 5.4 s p50 and 7.5 s p95. Haiku was slower in this environment, at 8.3 s p50.

Hook probe (requested by the architecture thread)

prototypes/phase0-spike/hook_probe/ installs a throwaway Claude Code project with async UserPromptSubmit and PostToolUse hooks and a sync Stop hook. It ran 3 live headless sessions (Claude Code 2.1.316).

  • All three hooks fired on every run. The payloads carry the prompt, tool name, input and response,

duration_ms, session_id and transcript_path, enough to feed grouping without reading the session store.

  • The Stop hook's {"systemMessage": ...} reached the person as a notice ("Stop says: …") and did

not enter the model's context.

  • A Python collector process costs 35 ms p50, 47 ms p95, 58 ms max (50 cold runs, wall time).

That is inside the 50 ms p95 budget with almost no margin. Use a compiled collector, or a tiny client that hands off to the running core, for the sync Stop hook.

  • Not tested here: Copilot CLI hooks (Copilot CLI is not installed or signed in in this

environment) and rendering in the interactive TUI (only the headless stream). Both were then measured on Windows; see the next section.

Hook probe on Windows (Claude Code and Copilot CLI)

Measured on Imran's Windows 11 laptop. Full detail is in prototypes/phase0-spike/results/hook-probe-windows.md and the raw numbers in hook-probe-windows.json.

  • Claude Code works end to end. All three hooks fired in 3 of 3 runs, and the async hooks did not

block the turn. The Stop card renders in the interactive TUI as ⎿ Stop says: <card text>. Claude Code adds the "Stop says:" prefix.

  • Copilot CLI can observe a turn but cannot show a card. Versions 1.0.104 and 1.0.105 were tested,

at repo level and at user level, both headless (-p) and interactive.

  • All six events fired: sessionStart, userPromptSubmitted, preToolUse, postToolUse, agentStop and

sessionEnd.

  • No hook output reached the person. That covers systemMessage, and progress lines with or

without temporary.

  • Copilot hooks are synchronous: "async": true is ignored, and every hook blocks the agent.
  • Collector cost on Windows is mostly process start-up. The collector's own work takes about 1 to

2 ms. Whole-process times over 50 runs:

Facts-first judge (rung-model spec, PR #3)

After the first run, the rung-model spec moved to facts first: the model answers narrow fact questions, and deterministic per-job rules place the rung (decision Q6). The prototype in aiq_spike/facts.py and run_facts.py reproduces this:

  • Model facts: F2, F4, F5, F6, F7 and F12, each with a confidence.
  • Log facts: F1, F3, F7 and F8.
  • F9 (reuse): repo reuse counts, simulated per corpus because a session cannot supply them.
  • Rules: the spec's illustrative rubric table.

Sonnet and Haiku each made two runs on both corpora (200 calls). The rule variants below are applied to the same saved facts, so any difference between variants comes from the rules alone.

Variant (Sonnet facts)Exact (dev / held-out)Within 1Uncertain
A: spec as written (F2 from logs only)0.27 / 0.300.70 / 0.60100%

Holistic judge, for comparison (Sonnet, excerpt)0.80 / 0.850.97 / 0.90n/a

What this shows:

  1. The facts are stable. Sonnet's two runs agreed on F4, F5, F6, F7 and F12 in 85 to 100% of

tasks, and on F2 in 75 to 93%. So facts-first is a sound base.

  1. The model's confidences are low, not its answers. It mostly answers 0.5 to 0.6, even when the

value looks right. At the spec's 0.7 fact threshold, most rules count as not met and tasks sink to rung 1. The planned fact check should set this threshold; picking it a priori is a guess.

  1. F2 as specified makes every CLI task Uncertain (variant A). With no git diff, nothing in a

CLI log gives the person's share of the change, and the CLI rows in the corpus have no git. AIQ needs the post-turn git diff for this fact.

  1. F2 does not separate Directed from Delegated in CLI agents. The agent writes almost all of the

change in both. In variant E, 16 of 34 Directed runs were placed on Delegated. The rubric needs a fact for what the rubric actually means: was a whole outcome handed over, with done criteria, or one piece or step?

  1. Factory should not require Orchestrated. All 4 Factory tasks, across both corpora, are a

team's versioned single-agent workflow. They also start with a typed command rather than a brief, so F4 fails. Factory should rest on F9 (reuse by others) plus automated checks.

  1. Rung 4 became reliable. Once one sub-agent with automated gates counts, the facts plus rules

placed all 8 Orchestrated runs correctly (holistic judge: 4 of 8).

Recommendation for the rung-model spec:

  • Keep facts-first. Its errors are in the rules, which can be fixed and explained.
  • Add the "whole outcome handed over" fact.
  • Base Factory on F9 plus checks.
  • Take F2 from git where it exists.
  • Set the fact threshold from the fact check.

Collecting the week of real sessions is now a fact check, not a rung labelling exercise: the person answers yes or no on the model-read facts of 20 to 30 of their own tasks.

Guarded hybrid (rung-model spec Q8)

The spec then moved to a hybrid. The model places the rung, and deterministic guardrails can only lower it:

  • Delegated needs F1, F13 and F6, and is ruled out by F12 or by F2 ≥ 50%.
  • Orchestrated needs Delegated plus F7, F8 and checks run by the agent.
  • Factory needs F9 with runs by others, plus checks run by the agent.

score_hybrid.py scores this offline. It pairs each Sonnet holistic judgment with a fresh Sonnet fact reading of the same task and run (100 pairs, with the new fact F13), against the two variants below:

At fact threshold 0.7 every variant is worse. The guarded hybrid falls to 0.71 exact, and the version with a fact floor to 0.80.

  • Guardrails that only lower cannot fix this judge's errors. Its errors are under-calls (rung 4

judged 3, rung 5 judged 3 or 4). Across 100 pairs, the guardrails lowered 11 placements at threshold 0.5:

  • 4 were correct placements that became wrong;
  • none fixed an over-call.

At threshold 0.7 they lowered 20 placements, and 11 of those had been correct.

  • **Rules are right where the facts come from logs and the repo, and wrong where the line is

judgment.** Rules alone place rungs 4 and 5 well, because F8 and F9 come from logs and repo metadata. They place rung 2 badly: 14 of 34 runs land on 3 and 12 on 1.

  • The best combination uses facts in both directions. The model places the rung, and guardrails

lower it at rung 3. Log- and repo-verifiable facts for Orchestrated and Factory set a floor that can raise the rung. That scored 0.88 exact and 0.98 within one, versus 0.82 and 0.94 for the holistic judge alone.

  • Caveats.
  • This variant was designed after seeing these results, on the same data.
  • The F9 reuse counts are simulated, so the rung 5 gain depends on repo metadata existing.
  • Treat it as the hypothesis for the fact check to confirm, not as a result.

Fact check rerun: 15 Copilot CLI sessions (2026-11-02)

Goal: firm up the three weak facts from the first run (F5, F6, F13) with more tasks, mostly Copilot CLI, because target users mostly use Copilot. Verdicts per fact and task, with reasons and no prompt text, are in prototypes/phase0-spike/results/fact-check-2026-11-02.json.

Method. Same as the first run, with three differences, all forced by the rules for this run (read-only on the laptop, start no programs there):

  • Sessions. 15 hand-typed Copilot CLI sessions from the last 60 days, copied read-only. Not a

random sample: picked from the 101 sessions outside set-aside folders (the automated-session folder rule, AIQ's judge and temp folders, the judge-session list), favouring sessions with follow-up prompts and leaving out logs over about 25 MB. One repeated session was dropped. Every one of the 15 is real work; none is an AIQ test prompt. No Claude Code sessions: ~/.claude is a protected folder for folder access, so it can't be read from a cloud session.

  • Fact reader. Haiku 5.5, given the spike's own fact prompt and minimised excerpt, run in the

cloud session. Not the person's copilot -p as in the product.

  • Grader. Opus 5.5, given a fuller transcript (up to 40,000 characters instead of 18,000), with

the grader rules from fact_check.py. Two extra verdicts are counted apart from right and wrong: can't settle (the transcript can't show it) and ambiguous (the answer depends on how the fact is defined).

  • Facts. All 10 facts on every task (150), not 5 per task. Log facts F1 and F3 were scored twice:

with the spike's readers and with the rung judge's rules in PR #24 (aiq_domain::rung).

What this says about the three weak facts.

  • F5 is fine now: 15/15. The first run's 1/3 doesn't recur. Caveat: most follow-ups here are new

questions, which the reader counts as "added information"; only 3 sessions have true retries ("try again", a repeated prompt), and the reader got all 3 right.

  • F6 can't be read from Copilot CLI transcripts for most tasks: 9 of 15 can't be settled. On the

6 that can, the reader is right on 3. Its misses go both ways: it credits checking where the person only reran the work, and misses it where the person tried the advice and pushed back. F6 is only readable when the agent runs checks or a follow-up shows the person tested or challenged the result.

  • F13 is close: 11 right, 1 wrong, 3 ambiguous. The 3 ambiguous tasks list what to deliver but give

no checks. Whether that counts as "done criteria" is a definition question, not a reading error.

  • New weak fact: F4 at 67%. All 5 misses credit "constraints" to requests that state a goal and

context but no limits, or score the first prompt on detail that came later.

Log-fact rules (PR #24). The spike's readers miss Copilot's apply_patch edits and dotnet test / Playwright runs; the PR #24 rules fix both. Two new faults in the PR #24 rules:

  • F1 counts scratch scripts. The agent's throwaway analysis scripts in the Copilot session folder

count as edits (2 of 15). A simple "documents only" rule for that folder would fail too: one agent wrote its deliverable Word document through a script.

  • F3 matches check words anywhere in a command. It matches "playwright" inside a string and

"pytest" in a folder pattern (2 of 15). It would also miss npm --prefix <dir> run test:e2e.

Against the bar. The spec needs each model fact right on at least 90% of check tasks. F4 (67%) and F6 (50% of settled, 60% unsettled) fail. F13 passes only if the ambiguous tasks go its way. Job, F5, F7 and F12 pass. Confidence: Inferred. The grader is a model, not the person. The sample is 15 hand-picked tasks from one person, mostly research. The reader ran outside the person's own Copilot.

Recommended changes (for the judge thread and the job packs):

  1. F6: treat it as unknown unless the log shows a check or a follow-up shows the person tested or

challenged the result. Don't let an unknown F6 cap research tasks at Assisted: today the Directed guardrail needs F6 yes, and a low-confidence fact counts as not met.

  1. F4: define "constraints" in the reader prompt with yes and no examples, and score the first

prompt only.

  1. F13: decide whether a list of deliverables with no checks counts as done criteria, and add that

example to the reader prompt.

  1. PR #24 log rules: separate scratch work from deliverables for F1. Match check commands by

command words, not substrings, for F3.

  1. Packs: most of this person's Copilot work is Other work, which the two alpha packs don't

cover. Worth weighing before coaching ships.

What would change this verdict

  • Real sessions, checked by facts (the main gate). Follow the rung-model spec's Q6, not a large

golden set. Collect one week of the team's own Claude Code and Copilot CLI sessions on each person's own machine. Each person confirms, for 20 to 30 of their own tasks:

  • the task boundaries and the job;
  • the model-read facts (yes or no).

Log facts are checked automatically. A 30 to 50 task expert sanity check per job covers rung placement. No-go if model facts are right on less than 90% of tasks (the spec's bar), job precision at 0.7 is below 90%, or grouping F1 is below 0.85. The synthetic tasks are cleaner than real work. Real sessions mix topics, wander, and include long auto-compacted runs.

  • Format check. The reader matches every field session-profile.py reads. Fields it does not

read were modelled from memory: Claude Code's <command-name> wrapper for slash commands, and Copilot tool argument names. Confirm them on one real transcript per surface.

  • Human edits are invisible. The rubric's "the person makes most of the edits" (the line between

rung 2 and 3) cannot be seen in CLI transcripts when the person edits in their editor. The VS Code collector or a git diff after the agent's turn would supply it. The synthetic tasks state it in the prompts, which flatters the judge.

  • Window size. Model grouping ran on the whole corpus in one call (41 to 66 turns). Real weeks

are larger, so the window and the rule for carrying tasks across windows still need designing.

Recommended changes

  1. Rung model / rubric (rung-model spec): add a repo reuse signal for rung 5, clarify rung 4

when sub-agents and gates are visible, and keep "mixed signals → lower rung" (it worked).

  1. Job packs: set the classification threshold to 0.7, and require the minimised excerpt for job

classification (the person can turn it off, at a known accuracy cost).

  1. Architecture: use model grouping in the slow path, rules only for live detectors, and a

non-Python collector for sync hooks. Default judge model: Sonnet, with Haiku as a cheaper option once its stability is measured on real data.

  1. Next probe: run the fact check on a week of real sessions (above), plus one Copilot CLI hook

end to end.
