ADR-0005: Collectors are fail-open, fire-and-forget, schema-versioned pipes

  • Status: Proposed
  • Note (2026-11-01): the Claude Code Stop hook budget is 100 ms p95 whole process (Imran). See note-20261101-hook-budget-100ms.
  • Date: 2026-10-31
  • Deciders: Imran (owner); drafted with Claude via /define-architecture

Context

The person's IDE and agents are the hot path (LOA F). NFRs: ≤ 50 ms p95 added to any hook; if the core is down the tools work unchanged. Claude Code's default command-hook timeout is 600 s and Copilot CLI's is 30 s (Claude Code hooks, Copilot CLI hooks), so the host will not protect us; the collector must enforce its own budget.

Decision

  1. Never block, never decide. Collectors never return a block/deny decision, never modify

prompts or tool results, and never write additionalContext (coaching is for the person, not the agent). They always exit success.

  1. Budget: each hook invocation does one non-blocking write to the core's local socket/pipe with a

20 ms connect+write timeout; total hook time ≤ 50 ms p95. On Claude Code, observation hooks run with "async": true; only the Stop hook that may render a card runs synchronously, and it waits ≤ 50 ms for a ready card. 2a. Runtime: the hook command is a tiny compiled client (aiq hook <event>, shipped with the core) that hands the payload to the running core over the socket and exits. No interpreter per hook: the Phase 0 probe measured a Python process at 35 ms p50 / 47 ms p95 / 58 ms max cold start, too close to the 50 ms budget for the synchronous Stop hook.

  1. Fail open with a bounded spool: if the core is unreachable, append the event to a user-only

spool file (≤ 1 MB, oldest dropped) and exit. The core drains it on start.

  1. Contract: aiq.event.v1 JSON Schema: event_id (UUIDv7), surface, surface_session_id,

seq, kind, ts, payload by kind. At-least-once delivery; the core upserts by event_id. Content fields are optional and subject to the retention policy (ADR-0002).

  1. Rendering: cards come back as aiq.card.v1. Claude Code: systemMessage from the Stop hook.

Copilot CLI: hooks cannot show the person anything (laptop probe, 2026-10-31), so AIQ renders a one-line tip in Copilot CLI's status line (statusLine command in ~/.copilot/settings.json, reading the pending card from the core), with aiq show for the full card (Imran, 2026-11-01; a desktop notification, alone or combined, may be revisited later). How long the tip stays before clearing is a person's setting ("Copilot CLI tip stays"). The default is to clear on the next prompt; the other choices are "for 2 prompts or 5 minutes, then a 1 tip waiting marker" and "stay until opened". The core owns that state, and the status-line command only reads it. VS Code: notification + status bar from the AIQ extension. Never additionalContext or exit code 2 to reach the person. 5a. Copilot hooks are synchronous, so the Copilot collector subscribes to the fewest events a detector needs (Phase 2: userPromptSubmitted, agentStop). Both hosts use exec form (command/exec + args), never a shell.

  1. Install at user level only: ~/.claude/settings.json and ~/.copilot/hooks/, never a repo's

.claude/ or .github/hooks/, so teammates never see or run AIQ hooks.

Alternatives considered

  • Synchronous request/response per hook: rejected; puts the core on the hot path.
  • Read session stores only (no hooks): kept as a fallback and for backfill, but alone cannot

coach in the moment.

  • Repo-level hook config: rejected; visible to and executed for teammates.

Consequences

  • Positive: AIQ can crash, upgrade or be paused with zero impact on the tools.
  • Negative: events can arrive late or (rarely) be lost when the spool is full; Tasks tolerate it.
  • Follow-ups: Claude Code and Copilot CLI hook semantics were run on Windows and Linux (Phase 0 probe, design spikes); the Copilot status line and VS Code agent-mode hooks still need a run.

Evidence

Hook docs linked above (read 2026-10-31). Phase 0 hook probe (Claude Code 2.1.316, headless, 3 live runs + 50-run bench; spikes/phase0/hook_probe/): async UserPromptSubmit and PostToolUse fire every turn and never block; a sync Stop hook's systemMessage renders to the person and does not enter model context; payloads carry prompt, tool name/input/response, duration, transcript path and session id, so hooks alone can feed Task grouping. Not yet exercised: Copilot CLI, interactive TUI rendering.
