UI & UX Capability Guide

Everything this repository knows about designing and building interfaces, and the order to use it in. Seven standards, one craft workflow, two linters, four templates and a persona council with real veto power.

The short version: settle what it does before how it works before how it looks. Pick the archetype from the job, not the data. Build the token system before the screens. Then let a deterministic control prove what you built, because a craft rule that lives only in prose is a memoir.

1. The stack

Seven standards, each owning one question. They compose downward: a lower layer constrains the one above it, so an unsettled layer below makes the layer above guesswork.

Each standard, what it decides, and its directive prefix.
LayerThe question it answersDirectivesStandard
Specification What must it do, how does it work, how does it look? Three layers, written bottom-up, each absent one marked N/A with a reason. S1–S10 specification-standards.md
Archetype What kind of interface is this? A determinism control that constrains generation before it starts. G1–G16 ui-archetype-grammar.md, ui-archetype-catalog.md
Craft process How do you get from a brief to a surface that looks designed rather than generated? DX1–DX25 ui-design-craft.md
Floors What must every interface meet regardless of taste? Tokens, complete states, motion, copy, WCAG 2.2 AA, performance. U1–U20 ui-interaction-design.md
Expert surfaces Extra rules when users are experts working with quantities: numeric legibility, colormaps, uncertainty, provenance. TQ1–TQ12 technical-ui-design.md
Detection Did the thing you built actually meet the floors? A 59-rule deterministic control, no model required. CD1–CD20 ui-craft-detection.md
Visual assets May imagery be generated, and under what conditions? Cost, provenance, privacy, alt text, non-determinism. VA1–VA22 ui-visual-assets.md

The one ordering rule that matters. Surface never precedes Structure. A settled UI over an unsettled UX layer is a block (S2), and the most expensive UI defect on record in this pack is an archetype chosen from the shape of the data rather than the shape of the task. Reading is parallel. Entering is serial.

2. Start here: pick your job

Six common situations and the path each one takes. When the surface already exists, review before you rebuild: replacing something you have not measured produces a differently flawed screen.

Nothing exists yet

No spec, no screens. Settle the functional and UX layers first, then design the surface.

/specify then /ui-design (create)

It exists. Is it any good?

Measure before diagnosing. You get counts, a rubric critique and a ranked plan, not opinions.

/ui-design (review)

It works but is not good enough

Review first, then rebuild the weakest layer. That is often the archetype, not the pixels.

/ui-design (elevate)

The design is approved. Build it.

Build against the tokens, implement every state, prove WCAG and the performance budget red-first.

/design-slice then /implement

Dense, scientific or quantitative

CAD, notebooks, dashboards, simulation, trading. Density is welcome, but hierarchy must rise with it.

/ui-design, which trips UI-T1

Marketing or landing surface

The one place generated imagery and cinematic motion genuinely earn their place.

/ui-design (trips UI-T2), then /visualize to produce the assets

3. Triggered standards

Two of the cards above say a job "trips UI-T1" rather than telling you to load a document. That wording is deliberate. The mode you run (create, review, elevate) is mutually exclusive: you are doing exactly one. The standards below are orthogonal and composable: any combination can be true at once, they apply on top of whichever mode you chose, and several often fire together. A CFD post-processing tool with a generated hero image trips two of them.

This is the same trigger mechanism the Testing Strategy uses for choosing tests, and it carries the same force. Map the surface against every row, apply all matching directives as a union rather than the first match, and treat a triggered-but-unmet directive as a gap the gate catches. The mapping happens at Stage 1, because the triggers reshape that stage: a trigger discovered in the definition of done has already cost you the archetype decision it should have informed.

Always on, plus the four conditional rows.
TriggerThe surfaceWhat it adds
Always Renders anything The floors (U1–U20), the craft process (DX1–DX25), the deterministic control (CD1–CD20), and the rule that an unsettled UX layer blocks the surface (S2, S7)
UI-T1 Serves an expert working with quantities: CAD, scientific visualization, notebooks, spreadsheet or financial modelling, simulation and risk, quant terminals The archetype comes from catalog section G rather than A to F. Perceptually-uniform colormaps, tabular unit-bearing numerics, uncertainty-first output, provenance, reactive recompute. A rainbow colormap, a unit-less quantity or a point estimate for a stochastic result is a correctness defect, not a taste one
UI-T2 Contains generated imagery, personas or motion The optional visual world, and the asset rules: mood never structure, supplementing never replacing real references, never the interface itself, committed rather than linked, with a manifest and alt text. Convenes the AI Systems Engineer and the Privacy lens
UI-T3 Fronts a model The wrong answer and uncertainty join empty, loading and error as first-class states. Name the HAX guidelines and the Shape-of-AI patterns. Oversight precedes any consequential action
UI-T4 Ships as a native client app (WPF, WinUI, Avalonia, Blazor Hybrid first) The run declares medium/platform/framework/distribution/accessibility API, cites the platform HIG, fills the native proof pack, and proves keyboard, accessibility tree, theme/high-contrast, DPI/windowing, OS integration, performance and signing/SmartScreen/notarization where applicable. HTML mockups and static craft scans are direction evidence only; they cannot clear native PASS.

A trigger is a claim about the surface, so establish it rather than assume it. "This is not really an expert surface" is a decision with consequences. When it is genuinely borderline, take the higher tier until evidence says otherwise.

4. The /ui-design loop

Five stages of the Rigor Protocol applied to an interface. The weight sits on the first stage (direction, before any visual artifact exists) and the fourth (critique, structure before surface).

What each stage decides and what it leaves behind.
StageWhat happensOutput
0. Interdict Do not generate a screen. One pass that decides direction, system and composition together averages all three into the generic default. In review mode: do not diagnose before you measure. Nothing. That is the point.
1. Open The direction brief in words: user and the state they arrive in, job-to-be-done, Archetype Signature chosen from that job, three adjectives and their opposites, named references with what is taken from each, anti-goals, constraints. Optionally then a visual world that makes the register concrete. Direction brief
2. Interrogate What is this surface for and explicitly not for. What does the archetype force and forbid. Enumerate the surface inventory: every component and its full state set. Surface inventory
3. Evidence Measure, then build the system before the screens. Both linters run. Establish platform guidelines from sources rather than memory. Write the motion inventory and the real copy. DESIGN.md, measurements
4. Disconfirm The gate. Rubric critique structure-before-surface, detector findings folded in with the severity floors, the tells self-check, the Simplifier's delete-list. Accessibility veto cleared by someone other than the author. Findings with severities
5. Converge Produce the artifacts and a ranked plan naming the single highest improvement-to-effort change. Mockup, review, hub node

The mockup is the deliverable that makes review possible. One self-contained HTML file, no build step and no CDN, opening over file://. It renders the hard states (empty, loading, error, partial, overflow) with realistic extreme content, and it ships a review harness that switches persona, viewport, state, theme, capability flags and reduced motion. A mockup showing one persona in one state with populated data is a screenshot with extra steps.

5. Commands

Run the workflow

/specify      # functional + UX + UI layers; settles Part B before Part C
/ui-design    # direction, design language, mockup, rubric critique
/design-slice       # component contracts, failure modes, test plan behind the surface
/implement    # build to the tokens, prove the floors red-first
/investigate  # a defect in running software enters here, never /implement

Run the controls

# inward: is the design language internally consistent?
python3 docs/ai-forward-pack/scripts/design-lint.py DESIGN.md --strict

# outward: does the built surface obey it? 59 deterministic rules, no model.
python3 docs/ai-forward-pack/scripts/ui-craft-gate.py src/ --markdown
python3 docs/ai-forward-pack/scripts/ui-craft-gate.py src/ --gate --a11y-obligation

# the detector reads DESIGN.md from the repo root or docs/. Install it once:
npm install --save-dev impeccable

Generate the imagery a surface shows

# which generation backend can this environment actually reach?
python3 docs/ai-forward-pack/scripts/visual-assets-setup.py --check
python3 docs/ai-forward-pack/scripts/visual-assets-setup.py --backends   # capability matrix
python3 docs/ai-forward-pack/scripts/visual-assets-setup.py --init       # assets dir + manifest + hygiene

/visualize    # board | asset | persona | motion

A consumer AI subscription is not API access. A Google AI Pro or Ultra plan grants the Gemini app, Flow and Whisk, and grants no programmatic API access at all. The API is a separate billing relationship, and image and video generation are not on its free tier. Establish which you hold before designing around it.

Keep the graph honest

python3 docs/ai-forward-pack/scripts/docs-graph.py derive     # frontmatter to index
python3 docs/ai-forward-pack/scripts/docs-graph.py validate   # dangling links, orphans
python3 docs/ai-forward-pack/scripts/docs-graph.py freshness  # stale and flagged

A gate that scanned nothing is not a passing gate. Confirm the detector matched a non-empty corpus and reported its own status. An empty result exits clean and proves nothing, and a chained shell block propagates only its last exit code.

Verify the archetype against the shape of the task, including on screens that already exist. A dashboard archetype applied to a data-entry job puts every control on screen at once and sequences nothing. Each component passes its own review; the screen is still wrong.

7. Gates and vetoes

Who can block, on what, and what clears it. The author never clears their own hard veto, even when one model is playing both roles in sequence.

Veto authority on UI work.
LensAuthorityBlocks on
UX & Accessibility Hard WCAG 2.2 AA, complete component states, token discipline on the visual surface
UX Researcher / IA Hard Evidenced need, coherent information architecture, flows covering alternate, error and recovery paths
Test Architect Hard Any correctness claim with no verification path; UI acceptance criteria that cannot fail
Privacy & Data Governance Hard Personal data or a real likeness sent to a generation provider
AI Systems Engineer Hard Non-determinism leaking into a deterministic artifact; a model capability with no eval
The Simplifier Soft Anything that does not earn its place. Emits a delete-list ending in net: -N
Craft detector Control Not a veto holder. It supplies evidence the lenses consume, and it gates CI

A clean detector run is a floor, never a verdict. It proves 59 specific patterns are absent. It cannot see whether the archetype fits the job, whether the information architecture lets anyone reach their goal, whether the empty and error states exist at all, whether the copy is true, or whether the focal point is defended. Reporting "detector clean" as "the design is good" is the most likely way this control gets misused.

8. Anti-patterns

The generic look, and what now catches it

Models trained on the same corpus converge on the same tells. The craft standard names them in prose; the detector catches the mechanizable ones in CI. This repository shipped three of them in its own templates until the detector was adopted.

Recognisable tells and their antidotes.

Thick coloured border on one side of a cardA full hairline in the semantic colour over a tinted groundside-tab

Generated imagery: the hard limits

Imagery, personas and motion that a UI contains may be generated. The interface itself may not: image models render illegible text and invented controls, so a generated screenshot makes a design look finished while encoding nothing anyone can build. Generate once, then download, optimise and commit the file. Provider results expire, and an asset that re-rolls per run is non-determinism inside a deterministic artifact. Never upload a real person's likeness or customer data.
