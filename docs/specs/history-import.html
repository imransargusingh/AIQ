Produced with AI-Forward /specify (Functional layer complete; UX outline; UI deferred to the aiq-home spec). Requested by Imran, 2026-11-01: "Is there a way to seed AIQ with data from sessions over the past few months (sessions that existed before a given repo was set up with AIQ) to classify those tasks?"

Design consequences:

  • Judge sessions must never be imported or observed as tasks. AIQ sets --session-id to a UUID it

generates, records it, and runs from its own working folder; readers and hooks drop those sessions.

  • Sealing. Pass --disable-mcp-server <name> for every server in the person's Copilot config, read

fresh before each batch, and confirm the tool list is empty from --log-dir once per batch; abort the batch if any tool is available. A throwaway COPILOT_HOME would seal fully but loses the sign-in and would need a token AIQ holds, which conflicts with "AIQ never reads the token". Installed plugins still load; accepted while tools are off and MCP servers are disabled (Imran, 2026-11-01).

  • Cost and speed. Batch several tasks' facts into one call where the prompt fits, to spread the

~20 s start-up; record --usage-output-file per call so judging cost is measured (TR-8).

  • AIQ deletes its own judge session folders (by recorded id) after reading the answer, by default;

a setting keeps them. aiq forget deletes any left over (Imran, 2026-11-02; rung-judge review S1).

Part A — Functional specification

Problem

AIQ only sees work from the moment its hooks are installed. A new user starts with an empty history, so the rung distribution and "opportunity to move up" views are blank for weeks. Most people already have months of AI sessions on disk. Those sessions can fill the history on day one.

Core scenario

  1. During setup, or later from Your data > Import history, AIQ lists the stores it found, with

session counts and date ranges per tool and per repo. Nothing is read beyond file metadata yet.

  1. The person picks which tools, repos and date range to import (default: everything found, Imran 2026-11-01), and sees the estimated judging

time at their daily budget.

  1. AIQ reads the chosen transcripts on device, groups turns into tasks, classifies each task's job,

computes log facts, and queues tasks for the judge.

  1. The judge works through the queue within the daily budget. Tasks appear in history marked

Imported as they are judged.

  1. The person can delete one imported task, all imported tasks from a source, or all imported tasks.

In scope / out of scope

In scope: Copilot CLI and Claude Code readers; discovery with counts; grouping, job classification, log facts and judge queue (reusing the live pipeline); automated-session detection; delete by source; re-import that skips sessions already imported.

Out of scope: Claude.ai web chats and M365 Copilot (not on disk); VS Code chat (later, H2); reading another person's sessions; recovering transcripts the tool already deleted; any upload.

User stories and acceptance criteria

  • US-1 Discover. Given AIQ is installed When the person opens Import history Then AIQ

shows each tool with session count, date range and size per repo, having read only file metadata and database row counts.

  • US-2 Choose. Given the discovery list When the person picks tools, repos and a date

range Then AIQ shows the number of sessions, the number left after automated sessions are set aside, and the estimated days to judge at the current daily budget.

  • US-3 Import. Given a confirmed selection When import runs Then transcripts are read

on device, tasks are grouped and classified, log facts are computed, and tasks are queued for the judge. The source transcript files are never modified.

  • US-4 Judge within budget. Given queued imported tasks When the daily judge budget is

spent Then judging stops for the day, and live tasks are always judged before imported ones.

  • US-5 No cards. Given an imported task is judged Then no coaching card is shown and the

daily tip cap is unchanged.

  • US-6 Automated sessions set aside. Given sessions that meet the automated rule (below) When

import runs Then they are set aside with no question asked: not judged, not shown as tasks, no fact counted. Discovery and Your data show one line per folder ("Executive_Presence: 5,946 automated sessions set aside · Include them"). Include them imports that folder's sessions as normal tasks; the choice can be reversed.

  • US-12 Automated sessions ignored live. Given a live hook fires for a session that meets the

automated rule, or in a folder whose sessions are set aside Then AIQ records nothing and never shows a tip. (Copilot hooks are user-level, so a pipeline's own CLI runs would otherwise reach AIQ.)

  • US-7 Idempotent. Given a session was imported before When import runs again Then

it is skipped (keyed by tool + session id + last-modified time); a session that grew since is re-read.

  • US-8 Delete. Given imported tasks When the person deletes one, a source, or all imported

Then the tasks, facts, judgments and any stored prompt text are removed from AIQ's store; the tool's own transcripts are untouched.

  • US-9 Lost history warning. Given Claude Code's cleanupPeriodDays is unset or under 90

When discovery runs Then AIQ says older transcripts are being deleted by Claude Code and shows how to keep them. AIQ never edits that setting itself.

  • US-10 Provider rule. Given an imported task from provider P When it is queued Then it

is judged only by P: Copilot tasks through copilot -p, Claude Code tasks through claude -p (H5).

  • US-11 Judge sessions excluded. Given AIQ ran a judge call through a CLI When discovery,

import or live capture sees that CLI's sessions Then sessions with AIQ's recorded judge ids are ignored.

Automated rule (tested on real sessions, 2026-11-01)

AIQ decides; the person only corrects. H = human turns in the session. A session is automated when H ≤ 1 and any of:

  • NI, non-interactive start. Claude Code: entrypoint = sdk-cli on its user records. Copilot CLI

records no prompt-mode marker (session.start keys checked), so NI is unknown there.

  • T, template. Its normalized first prompt (digits, URLs, GUIDs, paths, quoted strings replaced; first

200 chars; hashed on device) matches 11+ sessions in the same folder. Empty first prompts are excluded from template groups (they all share one hash).

  • B, burst. 50+ sessions started in the same folder within ±30 minutes.
  • F, folder prior (added after the test). The folder is over 80% automated by the signals above.

  • The Foresight Claude Code sessions (489, one prompt each, all hours, one autoresearch/* branch) were

started by Tacit, a tool of Imran's that a Copilot hook in that repo triggers and that runs claude headless (Imran confirmed as likely, 2026-11-01). Other AI tools calling a CLI in the background is a real pattern; the rule set them aside correctly.

  • H ≤ 1 is common in hand-run Copilot work too (median H = 1 in several hand-run folders), so H alone must

never decide; it always needs a second signal.

Domain model

Bounded context: History import, upstream of Task capture. One new aggregate:

  • ImportRun (entity): id, started, selection (tools, repos, range), counts found / imported /

set aside / failed. Invariant: a session belongs to at most one ImportRun.

  • ImportedSession (append-only fact; grain: one row per tool session read): tool, session id,

source path, last-modified, repo, ImportRun id, outcome (task / automated / skipped / error).

  • Tasks created by import are ordinary Tasks with origin = imported (Type-1 attribute, never

changes). Everything downstream (job, facts, judgment) is shared with live tasks; nothing is duplicated.

Non-functional requirements

QualityRequirement
PerformanceImport runs in the background core at low priority and never adds latency to a live hook. Discovery under 10 s for 10,000 sessions (metadata only)
Resource useRead transcripts as streams; never load a whole multi-GB store into memory; skip non-transcript files in Copilot session folders (the measured folder is 334 GB, mostly build trees)
ReliabilityA malformed file is logged as error for that session and import continues
CostJudging uses the existing daily budget (rung-model TR-8); imported tasks never exceed it
MeasurabilityEmit per run: sessions found, imported, automated, errors, read time, and queue depth; judge calls per day split live vs imported

Privacy and threats

  • Same rules as live capture: data stays on device; raw prompts kept until the person deletes them;

only the person sees it.

  • Transcripts hold more than live capture does (tool output, file contents). Import keeps only

prompts, replies needed by the model facts, and computed facts. Tool output and file contents are read to compute facts and then dropped. (To confirm in design: which reply text the judge needs.)

  • Judge calls go only to the provider that already saw the session (H5). A Copilot judge call must not

reach the person's MCP servers (work systems such as ticketing or mail); see sealing above.

  • A work account's transcripts may include work content; the setup caveat from rung-model Q2 is

shown again before import.

Part B — UX outline

Entry points: setup (step "Start with your past work?", skippable) and Your data > Import history. Flow: discover → choose → confirm (counts, set-aside automated sessions, estimated days) → progress (queue depth, judged so far) → history with an Imported filter. Failure paths: no stores found; store unreadable (permissions); budget spent (shows when judging resumes). Detailed screens go into the aiq-home spec once this spec is accepted.

Flagged risks and unknowns

  • Copilot CLI and VS Code transcript formats are undocumented and change between versions. Readers

must fail per session, not per run. AI-Forward's session-profile.py already parses both CLI formats and is the starting point (Verified it reads them; field coverage for facts Inferred).

  • F2 on imported tasks is weaker than live; imported rungs should carry lower confidence where F2

decides a guardrail.

  • Most history may be on other machines; import is per device.
