Design: label the kind of task with a small model

Approved by Imran on 2026-11-02 ("let's go with your recommendation", thread "Find out why no tips have fired").

Problem (measured)

From the tip decision log and store on the laptop, 2026-11-02:

  • Since the tips went live: 29 prompts, 9 new tasks. 8 of 9 stopped at the kind guess (no_guess).
  • Best word overlap (Jaccard) of a real first prompt with any of 122 judged tasks: 0.03 to 0.15. The bar

([coach] match_threshold) is 0.45; only 2 to 3 word prompts reach it.

  • Leave-one-out over the 122 judged tasks: the live rule 9 of 13 right; TF-IDF at most 15 of 32. No word

rule reaches the 8-in-10 self-check bar.

Decision

  1. Word guess first. coach::guess_type is unchanged and free. When it names a kind, nothing is sent.
  2. Otherwise ask for a label, off every clock that matters. The core (Service::next_rung) calls a

labeller the aiq binary wires in; it starts aiq label --task … --surface … --session … detached, on its own thread. The hook already returned (ingest has no reply), and the core never waits on a model (C9). Hook time is unchanged: nothing on the hook path changed.

  1. One sealed call, same provider, the person's own sign-in. aiq label reuses the judge's

ClaudeCli / CopilotCli: Claude Code claude -p in an empty folder, no tools, hooks off, no saved session; Copilot CLI with its own empty COPILOT_HOME (in label-work, not judge-work, which the judge sweeps under its lock), no tools, no MCP servers, its session id recorded as AIQ's own (US-11). Models: Claude haiku (kind-label-claude-model); Copilot the label model if set (kind-label-copilot-model), else the judge's Copilot model, else Copilot's default.

  1. What is sent: only the first prompt, secrets removed again, cut to 4,000 bytes, inside a per-call

fence. The system prompt is the judge's own JOB and TASK TYPE text, cut from rung::SYSTEM at run time, so the label and the judgment it is checked against share one vocabulary.

  1. What is stored: one append-only kind_label row per call (schema v8): ids, outcome, job, kind, both

confidences, model, request time, call time, tokens, cost. Never text.

  1. Decision. aiq label tells the core (Request::KindLabel, no reply). Service::on_kind_label

drops the label when the session has moved to another task, the task already has a guess, or label::accept fails (needs a pack job, a named kind, and both confidences at least 0.8, the coaching bar). Otherwise it writes a type_guess row with method = label and runs the same decision as a word guess: the kind's coached move, the accuracy pause (K6b, PR #59), tip answers, cooldown, habit, then the trigger engine's budget and quiet period. The card waits for the turn's end (Claude Code Stop, Copilot CLI status line) as before.

  1. Own self-check. D10 (check_guesses against the later judgment) now runs per method. Labels turn

off by themselves below 8 in 10 right with at least 10 checked, without touching word guesses, and the other way round. next-rung-tips on overrides both, as before.

  1. Switches and budget. Labels run only while background judging is on (PR #75) and

kind-label is not off. Their own daily budget, kind-label-daily, default 20, 0 to 500, counted from kind_label rows since local midnight. It is separate from the judge's budget because a label is one call and a judgment two, and the person can see and cap each. Set-aside and automated sessions never reach the decision, so they are never labelled.

Second try (2026-11-08)

Measured on Imran's laptop, 2026-11-08: one of three new tasks that day opened with a 15-character prompt; its label came back at 0.78 / 0.74, under the 0.8 bar, and the task got no tip although the prompts after it said what the task was. Only the first prompt was ever read.

  1. When the first label is not sure enough (label_unsure, not a failure, not a sure question), the next

later prompt of the same task with at least RETRY_MIN_WORDS (4) content words is labelled instead: aiq label … --prompt <event id>. A shorter reply ("ok go ahead") waits for the next one.

  1. If that later prompt arrives while the first label is still out, it is remembered and sent the moment the

first label comes back unsure.

  1. Once per task. The second label is the last (MAX_LABELS_PER_TASK = 2 in aiq label; LabelWait in the

core). It is stored under the task's id, so it decides the tip exactly as the first would have, and the self-check scores it against the same analysis of the whole task.

  1. No double tip. A task decides once: a type_guess row ends it, and a sure first label never retries. The

card engine's per-session budget still applies.

  1. The prompt sent is the later prompt alone, inside the same fence and system text (PROMPT_VERSION

unchanged, so the replay gate and its recorded answers stand).

  1. Counted: tip-funnel step label_retry, then that label's own end (decided, label_unsure,

label_failed, …). core.log coach.label label_retry_requested. The daily label budget covers both tries.

  1. The wait is in memory: a core restart between the two prompts forgets it, and that task keeps its first

label's end (label_unsure). assume: 4 content words separates an ask from a reply; confirm from the laptop's label_retry rows and their ends.

The main miss: a first prompt that reports a problem reads as ask_research/troubleshoot, and the task then fixes it, so the analysis says code_change/fix_bug. No prompt wording fixed it (the rewrite made those labels unsure and broke others), so label-1 stays. 0.1.22 stopped troubleshoot labels coaching.

A confirmation run on 60 fresh tasks (17:04Z, 60 premium requests, label-1 on gpt-6.1-sol) disproved that 8 of 10: 13 of 29 confident labels right with troubleshoot left out (14 of 37 with it). The miss is wider than troubleshoot. Any confident ask_research label was right 2 of 22 times (6 of 14 on the first 20). The task the person starts with a question mostly becomes a code change. Labels naming any other job were right 12 of 15 (4 of 4 on the first 20), 16 of 19 together. So label::NOT_COACHED_JOBS keeps every ask_research label from coaching. The rule was drawn from the 60, so the first 20 are its only out-of-sample check (4 of 4). Coverage falls to about a quarter of new tasks (19 of 78). Instrumentation

  • aiq status: labels today of the budget, answered, confident, median call time, and labels checked

against the judge (right of checked).

  • core.log: coach.guess with coach.outcome = label_requested | no_guess | decided | not_coachable and

method; coach.label with label_not_confident | label_task_moved_on | label_self_check_off.

  • Counter AIQ-COACH-LABEL-REQUESTED.
  • label.log (bounded): one line per label call or skip, with call time and wait time.
  • aiq export includes kind_label.
