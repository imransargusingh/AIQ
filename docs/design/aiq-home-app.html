Design: Phase 3 AIQ home app

Produced with AI-Forward /design-slice (v2026.10.19.4). Grounded in docs/specs/aiq-home.md (Parts A–C, Q1–Q6 decided), DESIGN.md, the signed-off mockup docs/mockups/aiq-home.html (https://claude.ai/artifact/QmFS15mdqQmETbbXfMoK3s), docs/architecture.md and the two earlier slice designs.

Goal state

GoalThe person opens AIQ home on Windows and sees, from their own local data, their tasks, tips and captured data, and can pause, change tip settings and delete everything
Done whenThe app builds for Windows in CI; Home, Tasks, Habits and tips, Your data and Settings render real store data; the keyboard and screen-reader checks pass; a laptop run shows Imran's real data
Not in scopeThe rung judge and anything it feeds (kept rate, rungs, next steps, task-type detail, "This doesn't fit"); setup; delete one item / older than; sharing; quiet hours; installer
TierT2 (new component, new trust-relevant reader of the private store)

Grounding: what this design must satisfy

Quoted from the spec and architecture:

  • "AIQ home adds no new aggregate. It is a set of read views (projections)…" (spec, domain model).
  • "Tasks still queued for judging are counted separately and never guessed" (spec, grain).
  • "Core down: AIQ home says so and shows the last stored data, never a blank screen" (spec NFR).
  • "Home interactive ≤ 1 s after launch … every view reads only the local store" (spec NFR).
  • "No network call from any view except the judge … and update checks" (spec NFR, privacy).
  • "Keyboard-first: every screen and action reachable from the keyboard; command palette (Ctrl+K)" (spec NFR).
  • "Pause is reachable in 1 key (P) from every page, and its state is visible on every page" (spec UX).
  • ADR-0004: "Rust core, hook client and Tauri shell; TypeScript extension and UI".
  • DESIGN.md §10: "Unavailable judge: views that need it say why and how to connect, and the rest works."

Responsibility

AIQ home shows the person what AIQ has on them and lets them steer it. It computes nothing that the core does not already own: tasks are derived with the same Task rule the detector uses, through one shared function.

Error and concurrency model

Reads open SQLite with SQLITE_OPEN_READ_ONLY and a 1 s busy timeout. The store runs in WAL mode (Store::open_with, verified by reading), so a reader does not block the core's writes and sees the last committed state. All reads of one snapshot run in one read transaction, so the numbers on a page agree with each other. A timeout surfaces as AIQ-HOME-STORE-READ with Try again. No write ever happens through the read connection (query_only pragma as a second guard).

Telemetry

Local only. Snapshot.status.read_ms (measured each read, shown on Your data); the Tauri shell logs each command's duration and error code to <data>/home.log (user-only, capped at 256 KB, rotated once). No remote telemetry (architecture).

Conformance notes

  • No model call anywhere in the app (LOA C9 holds; no T3 component).
  • No new trust boundary beyond the shell's WebView → command bridge, covered above.

Flagged risks

  • Live tasks before this change have no folder. Accepted (no backfill).
  • The Task rule (one session, idle gap 30 min) is the Phase 1 rule; grouping accuracy on real data is unproven (architecture risk). Inherited.
  • The keyboard and screen-reader check in the real WebView2 is a laptop check; CI runs axe in Chromium, which is close but not the same engine build. Flagged.
