Design: the task Kinds list, re-cut from real work

Imran asked on 2026-11-14 why a task had no Kind, what the full list was, and whether the list came from research into what engineers, PMs and data scientists do. It did not: it was a first guess of 2026-11-02 (design coaching-from-rungs, "Pack data"), adjusted twice from his own tasks. The research compared the list with his analyzed tasks and with published role studies, and proposed one re-cut. He chose "New list, re-analyze all unnamed" on a decision card the same day (19:49 UTC). This note records what ships and why.

Words: the code says judge and task_type. People read analysis and Kind. This note uses the people's words, and the code's names only in code font.

Goal state

GoalA task gets a Kind a person in that role would recognise, so recurring work can be seen moving up the ladder. Past tasks with no named Kind get the same chance, once
Done whenThe new list is the answer contract of the analysis and of the first-prompt label; every past analysis that names no Kind on the list is queued again exactly once; both accuracy sets are re-recorded and their gates pass; Imran approved the merge card that states the cost
Not in scopeA fifth job. Grouping the Kinds by area of responsibility on screen (proposed in the research, not decided). Kinds for data roles and for email (held until 10 real tasks exist). Changing the rung rules. The word rule for progress checks (#294)
TierT1 (analysis version bump, answer contract change, no schema change)
Fan-out cap0

From published studies (read on 2026-11-14 for the research; not read again for this note): role studies list activities, not kinds of result. Debugging, code review, documentation and planning are tasks of their own in the DORA 2025 report and the Stack Overflow 2025 survey. The old list had one Kind for all data work and none for decks, planning, review that changes no code, or steering work already running.

Decisions

#QuestionDecisionWhy
K1One version or several?One, `j7`. All list and job-line changes ship togetherEach new version decides again which past tasks to analyze. Several small versions would cost more than one
K2What is a Kind named after?The work, in the role's words. Not how it was handed over. So there is no "Building from a plan" Kind: feature covers itThe rung already measures the hand-over. A Kind must stay the same while its rung moves, or no Kind can be seen moving up
K3How long may a name be?Short enough for the status line. The longest is 35 characters; with today's tip texts there is room for 36. Eight names are shorter than the research proposedA name is printed inside a tip and a milestone on the Copilot CLI status line, which cuts a long line. Two tests fail on a name that no longer fits: aiq-core pack.rs (tip line, 125 characters) and tests/milestone_note.rs (milestone, 104)
K4What about a task that spans two jobs?One fixed order in the prompt: changed code, then something run or shipped, then a document, then an answer. The job lines are widened to name build plans, release follow-ups, progress checks, reviews, planning and source controlMeasured: 34 of the 92 tasks with no job were splits between two jobs. A task with no job gets no rung
K5What happens to a stored retired Kind?Its label still resolves (task_type_label reads both lists) until the task is analyzed again. A new answer may not name it. The analysis parse refuses an id no job offers (build_fix, criteria, notes). A retired pair whose id lives on under another job (code_change/review, code_change/explain) is placed as other, and the rules that accept a Kind never give one (task_type_named). The label parse refuses any pair its job does not offerThe store is append-only, so old rows keep old ids. One function decides "named on today's list" for the placement and the re-analysis rule
K6Which past tasks are analyzed again?Every task whose current analysis names no Kind on today's list, once: no job, the Kind other, no Kind recorded, or a retired Kind (list_outdated in crates/aiq/src/judge.rs). An analysis already at j7 is current whatever it named. A named Kind the list kept is never sent againImran's choice. The trial shows why: the new list named a Kind for 54 of 103 such tasks. A kept name is not worth a model call. Retired Kinds are included so that the rule is "not on the new list", with no exception to explain; that is about 1 task on the laptop
K7Who pays, and when?Each computer analyzes its own tasks, inside its own daily limit (500 tasks a day by default). The background check runs 2 minutes after AIQ starts and then every 10 minutes, while analysis is on and not paused. Order: tasks with no job first, then tasks never analyzed, then the rest, newest firstExisting queue (queue in crates/aiq/src/judge.rs); nothing new is built. K8The first-prompt labelPrompt version `label-3`. The label prompt cuts its job and Kind lines from the analysis prompt, so it changes with the list. Past tasks are not labelled againOne list for both readers. A label reads only new tasks
K9Is "Checking on progress" a Kind AIQ coaches?No. A task the analysis names progress, read as a sure Assisted with no goal given, is a progress check: no rung of its own, never coached (coach::is_progress_check). The word rule of #294 stays for analyses older than j7Imran chose on 2026-11-14 that progress checks get no rung. Without this, three such tasks in 30 days become a coached Kind: a Home snapshot test showed the row reading "coach". The words found 55 of his 68 progress checks, so the Kind can catch the rest. Marked assume: in the code, to be confirmed by the second-reader check
K10A one-line release noticeNo rung, like a progress check (Imran's card, 2026-11-14 20:05 UTC): a second reason, release_notice, on the path of K11. A task is one when the analysis names it "Releasing or publishing" and reads it as a sure Assisted with no goal given, and its first prompt is short (at most 25 of the person's own words) and says the release is already out: "0.4.2 is published" (coach::is_release_notice). A request to do a release ("publish 0.4.2") has no such word and keeps its rung. So does a task whose first prompt is deleted: its words cannot be read. A progress check is asked first, so "status of the release?" is a progress checkIn the trial, 21 of the 58 tasks that gained a rung were release work at Assisted. Counted as tasks, they would pull the ladder down. The words are measured. The bar was set before the count: the rule takes at least 8 in 10 of the Assisted release tasks whose analysis note says a release is out, and at most 1 in 10 of the tasks it takes opens with a release verb. The counting script (docs/investigations/rung-groups/release_notice_match.py, read-only, counts only) ran on Imran's laptop on 2026-11-15 over 747 analyzed tasks. Of the 37 sure Assisted release tasks, the rule takes 21: all 21 whose analysis note says a release is out (bar: 8 in 10), and none opens with a release verb (bar: at most 1 in 10). 19 of the 21 name a version number and none asks a question. Two words do all the work: "published" (20) and "released" (1). The script's 15 other phrases ("is out", "is live", "shipped" and the rest) marked none of them, so they are not on the list (coach::RELEASE_NOTICE_WORDS): a word with no evidence would be a guess, and a notice the words miss keeps its rung. On the laptop, sure Assisted goes from 532 to 453 on the ladder: 58 progress checks and 21 release notices, none both
K11How does a screen know that a task has no rung?One field that names the reason (no_rung: progress_check or release_notice), in place of the yes-or-no flag of #294. Every screen shows the reason where the rung would be: Home's counts, the task list, the Day view and the task's own page. The rung, the next rung and the next step the analysis gave stay stored and are never shown for such a taskA second reason is coming (K10), and one flag per reason lets a screen honour one and miss the other. K12Where is the count of such tasks kept?One count by reason (`NoRungCounts`) wherever the unsure count is: Home, each project and the split. K13How does Home name the analyzed tasks it leaves out?One short line of their own, the same words in each place: "Not on a rung: 1 unsure · 2 progress checks" on the ladder card, "Not counted: …" under the split and in the first-run card.
