Design: Day view, live rung trend, and goals inside a task

Imran, 2026-11-03: "I wonder if a better unit to reason about is 'session' (... a time-bounded set of tasks that represent a user's intent)." Then: "we could still provide users with a task-oriented view in near-real time with some indication of what the session is trending towards." He liked options A, C and D from the rendered options (https://claude.ai/artifact/7LGhvfgLTQTLkUq8w5AsB8) and asked for row context in A.

Evidence: tasks stay the unit (measured)

Read-only on Imran's laptop store, 2026-11-03: 1,708 prompts, 293 sessions, 810 tasks, 532 judged. These counts include 7 sessions stored twice (live and imported), which "Stop counting sessions twice" fixes: 805 tasks become 785.

QuestionMeasured
Sessions holding more than one task141 of 293 (48%)
Sessions with 2+ judged tasks that mix jobs / kinds64 of 98 (65%) / 82 of 98 (84%)
Back-to-back tasks in one session with the same job and kind57 of 335 (17%); two random tasks in one folder: 13%
Next task in another session, same folder, within 4 h, same job and kind26 of 137 (19%)
Tasks running at the same time as another session91 of 810 (11%)
Gaps between prompts inside a task of 10 to 30 minutes415 of 898 (46%)
Hand read of 30 tasks with 4+ prompts: one goal / two / three or more21 / 7 / 2 (one reader; 9 of 30 from one session)

So: the 30-minute cut already separates goals (17% vs 13% chance). Goals rarely span sessions. The gap is a goal change inside a task, in about 3 of 10 long tasks; long tasks are few, so roughly 3 to 5% of all tasks (Inferred from the sample). A shorter idle cut would split goals more often than it would catch a change.

Later steps (not built here)

Step 1: record the agent's actions live (its own thread, "Capture the agent's actions live"). C and D need to know what the agent did each turn. Today only imported history has that (the import summariser in crates/aiq/src/import.rs: tool counts, commands, files, sub-agents per turn); live stop events carry none (measured: 0 of the live stops, all 1,629 imported stops). Design agreed with Imran on 2026-11-03:

  • After each turn ends, the core (never the hook, rule RC; opening the transcript in the hook cost ~0.4 s on

the laptop) reads only the new part of the tool's own log, read-only. Claude Code: the transcript_path already in every event. Copilot CLI and VS Code agent mode on the Copilot target: the Copilot session log the core already reads at each turn end (crates/aiq-core/src/copilot_log.rs, PR #89).

  • Reuse the import summariser so live and imported turns match. One append-only row per turn, counts and

tool names only (no command text, no file names), behind a switch in Settings > What AIQ records.

  • Measure read time per turn from the first build. A failed read is "not recorded" plus a counter, never a

guess. Fix once, in the shared summariser, that Copilot's files stays empty when apply_patch runs.

  • Per-tool hooks were rejected: Copilot hooks run synchronously (ADR-0005), about 65 to 70 ms per tool call.

Coverage. VS Code agent mode on the Copilot target is covered by the Copilot log (6 of the 7 sessions stored twice were VS Code live sessions with Copilot CLI session ids). Not covered: VS Code agent mode on the Local target (runs no hooks), ask mode, inline chat. VS Code keeps chat-panel files per workspace (chatSessions, now .jsonl in Insiders, a format change since 1 November). Reading them is possible but is its own reader for an undocumented format; a field-names-only shape check comes first.

Step 2: C and D. C, a "Right now" card at the top of Home while a task is open: a step line of the estimated rung after each turn, the rung the task could reach, and the tip at the turn it applies to. D, the same trend in the existing status-line tip. Both are an estimate until the task ends; the judge's rung replaces it. Imran gave the go on 2026-11-03 ("build C and D"); built as designed in docs/design/live-rung-trend.md.

Step 3: goals inside a task. The judge marks where the goal changes, in the same call it already makes, and names a kind per part; stored as append-only segment rows, never by rewriting tasks. Before it goes live, hand-label goal changes in 50 to 80 tasks from many sessions and switch on only what beats the plain time gap. The Day view then draws a dashed line inside a block where the goal changed.

Parked: babysitting tip. Measured: 14 of 810 tasks were mostly status checks, 11 of them from one session of scheduled prompts, none live (detector precision 19 of 20 prompts, 13 of 14 tasks). Too concentrated for a tip.
