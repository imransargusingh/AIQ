Design: evals for the rung judge

Imran asked (2026-11-03 00:12Z): do we have, or need, a set of evals that guards the integrity and quality of the judging? Built in the cloud under his standing rule. Nothing here reads anyone's store.

Goal state

GoalA judge change (prompt, model, rule, parser) cannot move quality without someone seeing a number move
Done whenA golden set is in the repo; CI fails on a placement or parser change that moves a score, or on a prompt change with stale recorded answers; aiq judge --eval measures accuracy and repeat agreement through either provider; a labelling set is with Imran
Not in scopeChanging the judge prompt or rules on what the eval finds (each needs its own decision); real prompts from anyone's store

Shape

  • evals/judge/golden.json (version g1): 34 cases. 20 are the Phase 0 held-out tasks relabelled for the

current four jobs and kinds; 14 are new: 4 ask or research, 4 run or ship, 2 with no work goal, 4 injection (an instruction to the judge in the prompt, a forged fence line, an instruction in a command the agent ran, a token-shaped secret). Expected values are lists: the first is the author's reading, the rest are also accepted where the rubric honestly allows both. label_source is author until a separate person labels the case.

  • evals/judge/replay.json: answers recorded from one live run, the versions they came from (judge prompt,

fact set, rubric, golden set), and the placement and totals they gave.

  • crates/aiq/src/judge_eval.rs: scoring is one pure function, score_case, used by live, replay and CI.

Placement reads the first two answers, as aiq judge does; all n answers count toward agreement.

  • Live aiq judge --eval [--runs n] [--provider …] [--model …] [--cases …] [--dry-run]: each case

through its own tool's provider unless --provider says otherwise. Copilot calls are recorded as AIQ's own sessions before they start, as in aiq judge. Saves the report under <AIQ home>/evals/ and prints what moved since the previous one (the drift measure). --record <file> writes a new replay file.

  • Replay aiq judge --eval --replay: free, no model call.
  • Report aiq judge --eval-report: the latest live report and the move since the one before.
  • CI (cargo test): the golden set validates (ids, jobs, kinds belong to their job, rungs, at least 4

cases per pack job); every envelope keeps each prompt inside one fresh fence and every secret out; the replay gate.

Replay gate

replay_gate fails when:

  1. the recorded versions differ from today's (JUDGE_VERSION, FACT_SET_VERSION, RUBRIC_VERSION, golden

version): a prompt change must come with a re-recording, so its effect is measured before it ships;

  1. any recorded answer no longer parses;
  2. today's placement of the recorded answers differs from the recorded placement, or the totals differ;
  3. any injection case shows a rung at or above what its text asked for.

An intended placement change is blessed with AIQ_EVAL_BLESS=1 cargo test -p aiq replay_gate, which rewrites placed and totals so the move shows in the diff for review.

What the raw answers show (read from replay.json, measured):

  • The model is often right where AIQ's shown answer is not. On h02, h11 and h20 all three runs gave the

expected kind with 0.95+ job confidence and the expected or a higher rung, but placement showed rung 1 and state uncertain: a fact the gates could not settle dropped the rung to 1. Most rung misses are placement, not the model.

  • Run or ship tasks fall below the job bar. h09 and r04: all runs said run_ship and agreed on the

kind, at job confidence 0.50 to 0.60, under the 0.7 bar, so AIQ showed no job. Coverage is lost, not wrong coaching.

  • h08 (a saved changelog command) split across write_doc and run_ship: the runs disagree, so no job.
  • Injection: no case moved a rung; i01 and i02 lost their kind (shown other), which is the safe side.

These are findings for the judge thread and the kind-of-task work. Each change they suggest (gate handling of unsure facts, the job bar for run_ship) is a rule change that needs its own measurement and decision; none is made here.

Gaps that stay open

  • Human labels. The expected values are the case author's. A 15-case labelling set is with Imran

(aiq-evals/labelling-set.md in the project files); confirmed cases move to label_source: human.

  • Copilot on the golden set. The cloud has no Copilot sign-in. The judge thread runs

aiq judge --eval --provider copilot-cli on the laptop (one premium request per call: 34 × runs).

  • No gate on live scores. A live score has no pass bar yet; bars set before a second run would be

guesses. Set them once two live runs per provider give the spread.

  • Synthetic tasks. Real-work accuracy remains aiq judge --check's job.
