The estimate (T1)

aiq_domain::trend reads the log-fact half of the rung guardrails, turn by turn, over the turns that have ended.

EstimateRule (from the log)Guardrail it stands in for
Assisted (1)The agent made no edit (an answer or run job: looked nothing up), or the first prompt is under 20 words and not a slash commandF1 / F14, F4
Directed (2)The agent did the work, but the person has sent 3 or more promptsF12 (driven a turn at a time)
Delegated (3)The agent did the work from at most two promptsF1 / F14 with F4
Orchestrated (4)Also a spec or brief named, sub-agents ran, and the agent ran checks itself (answer job: sub-agents)F7, F8, F3 / F15

Factory is never estimated: F9 (a saved workflow) is not readable today. The job comes from the first-prompt label (PR #80) when it clears the judge's own bars (job 0.7, kind 0.7). Without it, edits count as the work.

Measured, golden set g1 (32 cases with a labelled rung), 2026-11-03. Exact 22 of 32, within one rung 29 of 32, higher than the label 4 of 32. The judge's recorded replay on the same set: exact 23 of 32, within one 29 of 32. trend_matches_golden (crates/aiq/src/judge_eval.rs) fails if a rule change does worse. The golden set is synthetic; the first live check is the estimate at a task's end against its judgment (later step).

assume: 20 words stands in for "goal, context and limits up front" (F4), and 3 prompts for "driven a turn at a time" (F12). Confirm: the end-of-task comparison above. If false: the estimate leans low or high on those tasks, and the judge's rung still replaces it.

Live limits. Live turns store counts and tool names only (no command text, no file names; design live-agent-actions). So live, AIQ cannot see that the agent ran a check or read a spec file. A code task then reads at most Delegated live; an answer task can still reach Orchestrated through sub-agents. A turn that was not recorded adds nothing; the estimate stays where the recorded turns put it, and no estimate shows until a yes is seen. A deleted first prompt gives no estimate rather than a guessed one.

Cost, measured from the first build

The status line already asks the core on every refresh. The trend adds one indexed query over one session's last day of events and one over today's kind labels, and reuses the coaching rows already built (it never rebuilds them on a status-line refresh). Each call logs core.trend_line with open, shown and ms; the status line's own timing log marks trend. assume: well inside the 50 ms render wait. Confirm: core.trend_line ms on the laptop after install. If false: cache the estimate per session and refresh it at each turn end.
