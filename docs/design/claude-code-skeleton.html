Responsibility

This slice turns "the person rephrased the same request three times in Claude Code" into one card under Claude's reply, without ever slowing or changing Claude Code. It is responsible for: capturing prompts from Claude Code hooks; storing them as append-only facts in the encrypted store; detecting re-prompts without new information inside one Task; deciding show / hold / drop under the budget; and rendering the card at the next Stop.

It is not responsible for: other surfaces (Phase 2), feedback and Habits (Phase 3), Job classification and signed packs (Phase 4), rung judging (Phase 5), the Tauri status page (Phase 6), showing held cards later (no next-pause surface exists yet), or tool-call capture (see "What is not captured").

As ADR-0002: dimensions plus append-only facts in one SQLCipher file per OS user. This design adds no new representation decision, so no new ADR. Enforced invariants and their tests

  • Fact tables (event, signal, card_decision, card_delivery, setting_change) have

BEFORE UPDATE and BEFORE DELETE triggers that RAISE(ABORT, 'AIQ-STORE-APPEND-ONLY'). Test: attempt an update and a delete on each; both fail. forget --all removes the whole file instead (ADR-0002), so it never needs to delete fact rows.

  • content allows DELETE and forbids UPDATE.
  • card_delivery has a unique index on (surface, surface_session_id) for in-the-moment cards.

Test: a second insert for the same session fails, even if the decision loop is bypassed.

  • Ingest is INSERT … ON CONFLICT(event_id) DO NOTHING. Test: replaying the same frame twice

stores one row and produces one signal (spool-replay property test, D2).

Migrations

Schema version in PRAGMA user_version. Phase 1 creates version 1. Later changes follow expand-migrate-contract: add columns or tables, backfill only from stored facts (never guess), remove old ones in a later release. A migration runs in one transaction; on failure the store stays at the old version and the core reports AIQ-STORE-MIGRATION and stays down (hooks still fail open). Rollback test: a failing migration leaves user_version and data unchanged.

Storage size estimate (architecture gate condition)

Inferred, not measured. Model: a heavy user sends 200 prompts a day across 300 working days; average prompt 600 characters; per prompt one event row (~250 bytes with index) and one content row (~650 bytes); signals and cards are negligible. That is about 180 KB a day, about 55 MB a year, about 110 MB a year allowing 2× for SQLite pages and indexes. Phase 1 stores no tool output; when PostToolUse capture arrives (tool output can be KBs per call) the estimate must be redone, and that is likely 10–50× larger. Gap that forced the model: no real week of usage yet; aiq status reports the store size and row counts so the dogfood week measures it.

    "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "\"<abs path>/aiq\" hook claude-code UserPromptSubmit", "async": true, "timeout": 5 }] }],
    "Stop":             [{ "hooks": [{ "type": "command", "command": "\"<abs path>/aiq\" hook claude-code Stop", "timeout": 5 }] }]

}

<abs path> uses forward slashes on every OS. The timeout: 5 is a safety net only; the client's own budget is 50 ms. Every AIQ entry carries the literal aiq hook claude-code so install and uninstall find exactly their own entries and never touch the person's other hooks.

aiq hook guarantees: always exits 0; never writes to stdout except one {"systemMessage": …} on Stop when a card is ready; never writes additionalContext, decision or continue; returns in ≤ 50 ms p95 (Stop) and ≤ 20 ms p95 for the hand-off on observation events.

How the pieces behave

Hook client (aiq hook claude-code <event>)

  1. Read stdin (cap 256 KB; more is cut). Parse leniently; on any parse error, exit 0 silently.
  2. Build aiq.event.v1.
  3. If the pause flag file exists, exit 0 without sending (nothing captured while paused).
  4. Connect to the core with a 20 ms budget; send one frame.
  • UserPromptSubmit: send ingest, close, exit 0.
  • Stop: send take_card with wait_ms = 30; wait up to 35 ms for the reply; if a card arrives,

print {"systemMessage": "<rendered card>"}; exit 0.

  1. If the connect fails: append the frame (without the token) to the spool file (≤ 1 MB; oldest lines

dropped), try to start the core detached (at most once per 10 s, guarded by a lock file), exit 0. No card is shown on a Stop that hit the spool.

The pause flag is a file because the hook must honour pause even when the core is down; aiq pause writes both the flag file and a setting_change row.

Core ingest and the decision loop

  • One listener thread accepts connections and parses frames. Parsed frames go onto one bounded channel

(capacity 1,024) to one writer/decision thread, which owns the store connection. One writer removes write races and makes the Coaching-session invariant a sequential check.

  • If the channel is full, the listener drops ingest frames and counts AIQ-INGEST-BACKPRESSURE;

take_card frames are never queued behind a full channel (they get {"card":null} immediately).

  • On start: open the store (key from the keychain), migrate, rebuild the detector working set for

Tasks active in the last idle-gap window, drain the spool in file order, then truncate it.

Task grouping (Phase 1 rule)

A Task is the prompts of one Claude Code session, split when more than 30 minutes pass between prompts. simplify: ceiling — a person who switches topics inside one session within 30 minutes gets one Task; upgrade trigger — the Phase 0 real-data week shows grouping F1 below 0.9 on Claude Code sessions, or Phase 2 needs cross-surface Tasks.

Re-prompt detector (reprompt.v1, Opportunity 1)

A prompt p in a Task is a re-prompt of the request when:

  • it is similar to an earlier prompt of the current request: Jaccard similarity of content-word sets ≥ 0.6 (words: lower

case, ≥ 3 letters, stop words removed, as in the Phase 0 spike); or it is a retry cue with no new request (pack list: "try again", "still not working", "that's wrong", "no, I meant", …); and

  • it adds no new information: no file path or @-mention not already in the Task, no pasted block

(code fence or ≥ 3 newlines), and at most 4 content words not seen earlier in the Task.

The detector keeps a running count per Task of re-prompts of the current request; a prompt that is neither similar nor a cue starts a new request and resets the count. When the count reaches the pack threshold (3), it emits one Signal with reprompt_count, the evidence event_ids, and a score = (similar re-prompts + 0.5 × cue-only re-prompts) / count. It emits at most one Signal per request.

assume: the 0.6 / 4-word / 3-count values catch real re-prompting without firing on normal follow-ups. Confirm with the Phase 0 real-data week (fact F5, "every re-prompt added new information"). If false, cards fire on productive iteration and erode trust; the values are pack data, so the fix is a pack change.

Trigger engine (rule in_moment.v1)

On each Signal, in the decision thread, in this order:

CheckOutcomeReason code
Pauseddroppaused

Decisions take well under 2 s (they are in-memory checks plus one insert) and are written as card_decision rows. "Show-ready" means the card waits for the next Stop in that session. Held cards are recorded only; nothing shows them later in Phase 1.

assume: 0.75 is uncalibrated. Confirm against the dogfood week. If too low, weak signals show; if too high, nothing shows. Pack data.

Take-card at Stop

When take_card arrives for a session: if stop_hook_active is true, reply null. Otherwise, if a show-ready card exists for that session, re-check the budget, insert card_delivery in the same transaction, and reply with the card. Delivery is recorded when the card is handed over, so a card is shown at most once (a client that dies after receipt loses that card; accepted below). If the Signal landed after this Stop (an async prompt hook arriving late), the card waits for the next Stop.

A show-ready card that is not delivered within 30 minutes (the idle gap that closes a Task; Phase 1 does not subscribe to SessionEnd) is expired (card_decision row drop/expired), so a stale card never appears in a later, unrelated turn.

Local day and cap

"Today" is the local calendar day at delivery, using local_offset_min stored on each delivery. A clock or time-zone change never re-opens a used budget for the same local date; the cap can only reset when the local date moves forward.

UI and interaction design (CLI medium)

Medium and conventions: text inside Claude Code's terminal UI, shown after Claude's reply as ⎿ Stop says: <our text>. Conventions: plain text, no colour or emoji carrying meaning, ≤ 80 columns per line where possible, works with screen readers that read the terminal line by line (spec NFR: "CLI renders as plain text with no colour-only meaning").

Tokens: none. The terminal owns colour and type; AIQ sets none. DESIGN.md is not produced for this slice (no visual surface of ours); it is required at Phase 6 (Tauri). Recorded deviation.

Rejected: an async runtime (tokio) — the core handles a handful of frames a minute; threads are enough (simplify: ceiling — about 1,000 frames/s; upgrade trigger — Phase 2 VS Code streams exceed it). Error and concurrency model

  • Hook client: no error is visible to the person or to Claude Code; every path exits 0 within

budget. Errors are counted in a tiny user-only hook-errors counter file read by aiq status.

  • Core: one writer thread; one transaction per frame; delivery check-and-insert in one transaction.

Concurrent take_card calls for the same session are serialised by the writer, and the unique index backs it up.

  • Ordering: prompts within a session are ordered by event_id time (UUIDv7 ms). Two prompts

within the same millisecond cannot occur from one person typing; ties break by arrival.

  • Idempotency: event_id for events; card_id for decisions and deliveries.
  • Cancellation/shutdown: on SIGTERM / console close, the core stops accepting, drains the channel

(≤ 1 s), closes the store. Unflushed frames are lost; the hook already exited 0.

  • Single instance: the core holds an exclusive lock file; a second aiq core exits with

AIQ-CORE-ALREADY-RUNNING.

What is not captured in Phase 1

PostToolUse (tool names, inputs and outputs), transcripts, the working directory, and session end. Opportunity 1 needs only prompts. Capturing less is smaller and more private. PostToolUse returns with the detectors that need it (Opportunities 2 and 3).

Telemetry

All telemetry is local and never leaves the device (no exporter, US-6). RFC 9457 does not apply: there is no HTTP surface.

  • Spans (`tracing`): hook.run (attrs: aiq.surface, aiq.hook_event, aiq.outcome),

core.ingest, core.detect, core.decide, core.take_card. Each frame carries a trace_id generated by the hook client (W3C format, 32 hex), so a card's decision can be traced to the hook run that produced it (O2–O4).

  • Logs: JSON lines to the user-only log file, OTel severity names, no prompt text (O1, O5, O11).
  • Stable error codes (one registry, `aiq-contracts::codes`): AIQ-HOOK-PARSE,

AIQ-HOOK-SPOOLED, AIQ-HOOK-STOP-TIMEOUT, AIQ-SPOOL-DROPPED, AIQ-SPOOL-BAD-LINE, AIQ-API-AUTH, AIQ-INGEST-SHAPE, AIQ-INGEST-BACKPRESSURE, AIQ-DELIVERY-CONFLICT, AIQ-STORE-KEY, AIQ-STORE-OPEN, AIQ-STORE-MIGRATION, AIQ-STORE-WRITE, AIQ-STORE-APPEND-ONLY, AIQ-CORE-ALREADY-RUNNING, AIQ-CORE-START-BACKOFF.

  • Metrics (counters and one histogram, shown by `aiq status`): events ingested by kind;

signals; decisions by outcome and reason code; cards delivered today; hook duration histogram (p50/p95 per event, measured by the client and sent in the next frame); spool lines; store size. Labels are bounded (surface, event kind, reason code); never session ids (O13).

  • Operator questions answered: How long does a hook take? (histogram) How often do cards show vs

hold? (decisions by reason) Did it fail? (error counters) How big is the store? (size).

  • Load-bearing telemetry tests (O12): hook duration is recorded on every run; decision reason codes

appear in aiq status; no prompt text in any log.
